## Current language behavior

`getElementLanguage(element)` currently returns:

1. `element.closest("[lang]")?.lang`
2. `element.ownerDocument.documentElement.lang`
3. `"zh-CN"`

Limitations:

- self and ancestor are not distinguishable for diagnostics/tests;
- Shadow Root host ancestry is not traversed;
- tags are not canonicalized or validated;
- no persisted user preference exists;
- no text-based fallback exists;
- the final hard-coded value bypasses configured `locale`.

## Existing reusable contracts

- `ReadingController` already resolves accessible text immediately before speech.
- `SpeechController.speak(text, lang, rate)` already has the correct explicit language boundary.
- `BrowserSpeechAdapter` already assigns `options.lang` to `SpeechSynthesisUtterance.lang`.
- Speech request IDs already suppress stale callbacks after interruption.
- `ReadingController.updateConfig()` already receives live config changes.

## Preference constraints

- `PreferenceStore` uses a versioned payload and an in-memory fallback.
- Parsing currently requires every v0.1 preference field.
- A new language field should be optional so old payloads remain valid.
- The language feature can expose a private preference provider now; the next voice-selection feature can add the user-facing writer.

## Tool messages versus page content

- Page content is read by `ReadingController` and should use DOM/text resolution.
- Region, tabs and toolbar messages are generated by the tool itself and currently use `activeConfig.locale` through `announce()`.
- Allowing a host document `lang` to override tool-authored Chinese templates would make those messages use the wrong voice, so the two paths should remain explicit.

## Recommended no-dependency approach

- Canonicalize with `Intl.getCanonicalLocales` / `Intl.Locale` when available.
- Provide a small BCP 47 casing fallback.
- Detect only common script groups with Unicode character properties and a confidence threshold.
- Return no detection on ambiguity and continue to the configured default.
